# Orders — Java 21 / Spring Boot 3

Реализованы API обоих заданий, восстановление заказов, исходящие события и бонусы.
Изменения ограничены orders/. Внешние API взяты из contracts/.

## Запуск

Из корня репозитория, в среде с Docker Compose v2 и make:

```sh
docker build orders/
make up
make scenarios TASK=1
make scenarios TASK=2
```

Тесты и JAR, при установленных JDK 21 и Maven:

```sh
mvn -f orders/pom.xml verify
```

Для PostgreSQL-тестов нужен работающий Docker. Без него класс
PostgresIntegrationTest явно пропускается Testcontainers; зелёная сборка
в такой среде НЕ означает прохождение интеграционных тестов.

Поддерживаются PORT, DATABASE_URL, PAYMENT_URL, INVENTORY_URL, EVENTS_URL.
DATABASE_URL принимает postgres://user:password@host:port/db?sslmode=disable
и jdbc:postgresql://host:port/db. Для JDBC-формы логин/пароль можно передать
через SPRING_DATASOURCE_USERNAME / SPRING_DATASOURCE_PASSWORD.
Flyway создаёт схему; /healthz проверяет доступ к БД после запуска приложения.

## Инварианты и обработка

POST /orders проверяет тело, рассчитывает сумму с проверкой переполнения int64,
создаёт UUID и сохраняет неизменяемую сумму и позиции. Только после коммита
возвращает 201 с pending. В обработчике HTTP нет сетевых вызовов к соседям.
GET возвращает сохранённый статус и сумму; неизвестный ID даёт 404.

Сохранённые этапы:

| Этап | Действие | Следующее состояние |
|---|---|---|
| RESERVE | Идемпотентный POST /reservations с order_id | PAY |
| PAY | Проверка результата / списание с постоянным ключом | paid или CANCEL; при неизвестном результате остаётся PAY |
| CANCEL | Идемпотентный DELETE /reservations/{order_id} | rejected только после успешного ответа |
| DONE | Обработка завершена | paid либо rejected |

Ключ Payment: order:<UUID заказа>. Он восстанавливается из сохранённого ID;
тело всегда содержит тот же order_id, amount_cents и RUB.
Повтор с этим ключом безопасен именно по контракту Payment, в том числе
если предыдущий запрос ещё исполняется. Никакой новый ключ при retry не создаётся.

Перед повторной попыткой Payment выполняется GET /payments?order_id=...
Списание признаётся успешным только при captured и совпадении заказа, суммы
и валюты. Пустой список не доказывает отказа: предыдущий запрос ещё может
выполняться. Повторный POST всё равно защищён исходным ключом.
Только 402 переводит процесс к компенсации. 500, timeout, потеря ответа,
неожиданный ответ и ошибки контракта сохраняют pending.

Четыре обработчика заказов и четыре обработчика событий имеют отдельные
лимиты занятости. Один проход берёт ограниченный пакет, очередь задач
в памяти не растёт вместе с числом заказов: задания хранятся в PostgreSQL.
Повторы идут с экспоненциальной задержкой до 5 секунд; для заказов добавлен jitter.
Число попыток за проход ограничено, но общий срок восстановления не ограничен:
временная недоступность не превращается в бизнес-отказ.

После сетевого сбоя Payment circuit breaker закрывает доступ на 5 секунд,
затем допускает одну пробную операцию. В обычном состоянии параллелизм
ограничен четырьмя обработчиками. Таймаут соединения 500 мс, ответа Payment
3500 мс, Inventory и Events — 700 мс. Эти ожидания идут только в фоне.
500 повторяется через backoff; неизвестный результат никогда не компенсируется
как банковский отказ.

## Транзакции и восстановление

Захват — один UPDATE с подзапросом SELECT FOR UPDATE SKIP LOCKED.
В БД сохраняются lease_token, lease_until (15 секунд), attempts и этап до HTTP.
SQL-запрос завершён и соединение возвращено в пул до сетевого вызова.
Изменение состояния допускается только при совпадении lease_token:
устаревший обработчик не перезапишет работу нового.

| Момент падения | Почему восстановление безопасно |
|---|---|
| До внешнего запроса | Заказ и этап уже сохранены; после истечения lease повторяется тот же этап |
| Во время запроса / после списания без ответа | GET находит capture либо повторяется исходный ключ, без нового списания |
| После ответа до записи результата | Повтор резерва по order_id, оплаты по ключу или снятия резерва идемпотентен |
| После paid до публикации | paid и outbox зафиксированы одной транзакцией |
| После публикации до отметки sent | Повторяется тот же сохранённый event id |
| Во время начисления бонусов | Inbox и баланс фиксируются либо откатываются вместе |

paid и создание outbox записываются одной короткой @Transactional операцией.
Из outbox публикуется order.paid с сохранёнными id, order_id и occurred_at.
Только HTTP 202 помечает запись sent. После потери ответа возможны копии
с одинаковым id, что соответствует контракту шины.

Для delivery.confirmed первичный ключ inbox — id события. INSERT ON CONFLICT
DO NOTHING и атомарное увеличение бонусного баланса выполняются одной
транзакцией. Параллельный дубликат ждёт исхода первой транзакции и не
начисляет бонусы повторно. Заказ для начисления искать не нужно.

## Ограничения

- Противоречие контрактов: Orders разрешает цену 0 и тем самым нулевой итог,
  Payment требует amount_cents >= 1, а бизнес требует реального списания для paid.
  Такой заказ принимается с 201, резервируется и остаётся pending без вызова
  Payment и без события order.paid. Нельзя безопасно выбрать конечный статус
  без уточнения контракта: rejected разрешён только при банковском отказе.
- Breaker локален процессу. Стенд требует один экземпляр Orders.
  Для нескольких экземпляров общий лимит обращений к банку нужно координировать.
- Lease защищает записи в БД, но не останавливает уже отправленный HTTP.
  Безопасность повторов опирается на идемпотентность внешних операций.
  Произвольно долгие остановки процесса между захватом и сетевым вызовом,
  особенно при нескольких экземплярах, потребуют дополнительного протокола
  координации Inventory, не предусмотренного текущим контрактом.
- Постоянные ошибки внешнего контракта остаются pending и требуют вмешательства.
  Данные inbox/outbox сохраняются без очистки, чтобы не нарушить дедупликацию.
- Гарантия 1 секунды относится к отказам соседей при доступной БД.
  При недоступности самой PostgreSQL надёжно принять новый заказ невозможно.
- Повтор самого POST /orders создаёт новый заказ: клиентский ключ идемпотентности
  для этого эндпоинта контрактом не предусмотрен.

```sh
sudo make scenarios TASK=1 RESULTS=orders/results TOKEN_FILE=orders/target/.mocks-token STAND_INFO=
sudo make scenarios TASK=2 RESULTS=orders/results TOKEN_FILE=orders/target/.mocks-token STAND_INFO=
```

совместимости API: mvn -B verify -Dapi.version=1.44.
Тесты выполнялись в сборочном контейнере Java 21 с подключённым Docker-сокетом.
